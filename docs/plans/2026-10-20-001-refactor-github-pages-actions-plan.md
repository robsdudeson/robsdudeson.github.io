# Migrate GitHub Pages Deployment to Actions

## Overview

Replace GitHub Pages' legacy branch builder with a repository-owned GitHub
Actions workflow. The workflow will build the Jekyll site from this repository's
locked Ruby dependencies and deploy only `_site`.

This addresses both actionable warnings in run `39452615969`: the legacy Pages
builder cannot satisfy the Gemfile, and its old artifact action emits the Node
20 deprecation warning. It also keeps source files such as `AGENTS.md` and
Nix tooling out of the published artifact.

---

## Problem Frame

The current Pages source is `main` at `/` with GitHub's legacy build type. That
managed workflow completed successfully, but it:

- warns that the `github-pages` gem cannot satisfy `Gemfile` dependencies;
- runs an artifact action that targets deprecated Node 20; and
- publishes from the repository source tree rather than an explicit build
  artifact.

The Node and runner notices are generated by GitHub's managed workflow and
cannot be fixed in repository files. A custom Pages workflow is the supported
route when a site needs its own dependency set or build steps.

---

## Requirements Trace

- R1. Deploy the existing site through GitHub Pages without changing public URLs
  or site behavior.
- R2. Build with the dependencies declared by this repository rather than the
  managed Pages environment.
- R3. Remove the legacy builder's Gemfile and Node 20 warnings.
- R4. Publish only generated site output.
- R5. Keep local and CI validation aligned.

---

## Scope Boundaries

- Do not redesign the Jekyll site or change the Midnight theme.
- Do not remove `faraday-retry` merely to appease the legacy builder; retain it
  unless dependency review proves it is unused.
- Do not attempt to suppress GitHub platform notices by filtering logs.
- Do not add a third-party deployment service.

---

## Context & Research

### Relevant Code and Patterns

- `Gemfile` declares `github-pages ~> 232` and `faraday-retry`.
- `bin/verify` already provides the intended local build contract: resolve
  Bundler dependencies and run `jekyll build --strict_front_matter`.
- `flake.nix` supplies Ruby 3.3 and Bundler locally.
- `.gitignore` currently ignores `Gemfile.lock` because the repository used
  GitHub's native Pages builder.
- No `.github/workflows/` directory exists.

### External References

- GitHub's custom Pages workflow guidance requires a build job that uploads the
  generated static artifact and a deploy job with `pages: write` and
  `id-token: write` permissions.
- Jekyll's GitHub Actions guidance recommends building with the repository's
  selected Jekyll dependencies and caching Bundler dependencies.

---

## Key Technical Decisions

- **Use GitHub Actions as the Pages source:** it is the only route that fixes
  both actionable warnings and lets CI use this repository's dependency set.
- **Upload `_site` only:** this preserves a clear source/build boundary and
  prevents repository guidance and development tooling from becoming deployed
  files.
- **Commit `Gemfile.lock`:** once CI owns the Ruby bundle, the lockfile becomes
  the reproducibility contract for local and hosted builds.
- **Use maintained, Node-24-compatible Pages action releases:** choose the
  current GitHub-supported majors at implementation time and confirm their
  runtime support from their release metadata. Do not carry forward the legacy
  artifact action that targets Node 20.
- **Keep deployment on `main`; build pull requests without deploying:** this
  preserves the current publishing behavior while making changes observable
  before they reach the public site.

## Open Questions

### Resolved During Planning

- **Which deployment model best addresses the warnings?** A repository-owned
  Pages Actions workflow; a Gemfile-only cleanup would leave the Node warning.
- **Should source files be published?** No. The deployment artifact will contain
  only `_site`.

### Deferred to Implementation

- **Exact action majors or immutable commit pins:** select them from GitHub's
  current official Pages workflow guidance and verify their Node 24 support.
- **Whether `faraday-retry` is still needed:** inspect the resolved dependency
  graph before removing any direct dependency; it is not a required part of the
  migration.

## Implementation Units

- [x] U1. **Make Bundler resolution reproducible for CI**

**Goal:** Turn the repository's Ruby dependency resolution into a committed CI
contract.

**Requirements:** R2, R5

**Dependencies:** None

**Files:**
- Modify: `.gitignore`
- Create: `Gemfile.lock`
- Modify: `.tool-versions`
- Review: `Gemfile`

**Approach:** Stop ignoring `Gemfile.lock`, pin `.tool-versions` to the Ruby
version used by local tooling, resolve dependencies, and commit the resulting
lockfile. Keep the
existing dependency declarations unless review identifies a genuine unused
dependency. Ensure the lock resolves the Jekyll and plugin versions used by the
site.

**Patterns to follow:** `bin/verify`, `flake.nix`, and the existing Gemfile
constraints.

**Test scenarios:**
- Happy path: a clean checkout resolves the locked bundle without changing the
  lockfile.
- Integration: the locked bundle builds the current posts and Midnight remote
  theme with strict front matter.

**Verification:** Local validation uses the committed lockfile and produces the
same `_site` output without dependency-resolution changes.

---

- [x] U2. **Add a least-privilege Pages workflow**

**Goal:** Build the site in CI and deploy the generated artifact through GitHub
Pages.

**Requirements:** R1, R2, R3, R4, R5

**Dependencies:** U1

**Files:**
- Create: `.github/workflows/pages.yml`
- Reuse: `Gemfile`, `Gemfile.lock`, `_config.yml`, `bin/verify`

**Approach:** Define separate build and deploy jobs. The build job checks out the
repository, configures Pages, installs the repository's selected Ruby version,
restores/caches Bundler dependencies from `Gemfile.lock`, and runs the same
strict Jekyll build contract as local validation. Upload only `_site` as the
Pages artifact. The deploy job depends on a successful build and receives only
the Pages and OIDC permissions GitHub requires. Trigger builds for pull
requests and `main`; guard deployment so it runs only for a `main` push or an
intentional manual deployment.

Use current official Pages actions that run on supported Node versions. Pin
third-party action references according to the repository's chosen supply-chain
policy; GitHub-maintained actions may use reviewed major versions if that is the
accepted maintenance trade-off.

**Patterns to follow:** GitHub's custom Pages workflow documentation and the
command behavior in `bin/verify`.

**Test scenarios:**
- Happy path: a push to `main` builds and deploys the site successfully.
- Integration: the uploaded Pages artifact contains generated `_site` content,
  including the post URL already in production, but does not contain repository
  source files such as `AGENTS.md`, `flake.nix`, or `bin/new-post`.
- Error path: an invalid post front matter change fails the build job and does
  not run deployment.
- Pull request: a pull request runs the build job without changing the live
  Pages deployment.

**Verification:** The workflow uses the locked bundle, has no legacy-builder
Gemfile warning, and does not produce the legacy artifact-action Node 20
warning.

---

- [ ] U3. **Switch the repository's Pages source and validate rollout**

**Goal:** Move the live site from legacy branch publishing to GitHub Actions
without an availability or URL regression.

**Requirements:** R1, R3, R4

**Dependencies:** U2

**Files:**
- Modify: `README.md`
- Modify: `AGENTS.md`
- External configuration: GitHub repository Pages settings

**Approach:** After the workflow is present on `main`, change the Pages build
source in repository settings from branch deployment to GitHub Actions. Trigger
or await one deployment, then verify the live site, homepage pagination,
existing Blu-ray post permalink, HTTPS, and the deployment environment URL.
Update project guidance so contributors know that pushes invoke the owned
workflow and that only `_site` is deployed.

**Patterns to follow:** Existing public-push guidance in `AGENTS.md` and the
local commands documented in `README.md`.

**Test expectation:** none -- this is an operational configuration change;
verification is the post-deployment smoke check above.

**Verification:** GitHub Pages reports GitHub Actions as its source, the latest
workflow deployment is successful, production URLs remain reachable, and the
legacy dynamic `pages-build-deployment` run no longer handles site builds.

---

## System-Wide Impact

- **Deployment:** publishing moves from GitHub's implicit branch builder to a
  visible repository workflow.
- **Dependency lifecycle:** `Gemfile.lock` becomes version-controlled and must
  be updated deliberately with dependency changes.
- **Public artifact:** only generated `_site` content is deployed; repository
  source remains in Git but no longer enters the Pages artifact.
- **Unchanged invariants:** `main` remains the publishing branch, the hostname
  and HTTPS configuration remain managed by GitHub Pages, and local verification
  continues through `bin/verify`.

---

## Risks & Dependencies

| Risk | Mitigation |
| --- | --- |
| A custom workflow deploys before Pages is switched to Actions | Land and review the workflow first; switch the Pages source only after it is present on `main`. |
| A dependency lock changes site output | Build locally and compare the generated site; use the first hosted deployment as a smoke test. |
| Incorrect workflow permissions block deployment | Use GitHub's documented `pages: write` and `id-token: write` deploy permissions, scoped to the deploy job. |
| Updating action versions reintroduces a deprecated runtime | Review action release/runtime support during dependency updates and keep deployment CI observable. |
| A source file leaks into the public site | Upload `_site` explicitly and inspect the first Pages artifact. |

---

## Documentation / Operational Notes

- Update `README.md` and `AGENTS.md` to name the owned Actions workflow as the
  public deployment path.
- Treat the first Actions deployment as a rollout checkpoint: inspect workflow
  annotations, artifact contents, the published URLs, and the Pages settings.
- Keep the existing public-push scan before pushes; CI artifact isolation is
  additional protection, not a substitute for content review.
